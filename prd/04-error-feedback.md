# 登录交互优化（含工作台错误提示）

> 状态：登录交互方案已由 chen 确认（2026-11-13）。第 6 节已拍板：写操作超时/断网统一直接报错，不加「可能已生效」。架构师技术方案已出具（`docs/plans/2026-11-13-login-interaction.md`），P0 已交开发和测试。待决仅剩页面级 403 文案。  
> 日期：2026-11-13  
> 提出人：chen  
> 范围：只出产品方案，不改业务代码，不改原型。技术方案由架构师出具，并由架构师安排开发和测试。

## 1. 背景

这次要改的不是「把几个错误码换个文案」，而是**重做登录交互**。

现网登录在后端库不可用时返回 **503**，且**不会下发会话 Cookie**，结果是确定失败。前端却把它（以及所有未列入「确定失败」的状态）标成 `uncertain`：锁住登录按钮，要求先点「查询当前会话」，再点「我已了解，允许手动重新登录」。文案绕，步骤也没有意义——库异常时 `GET /v2/auth/me` 同样只会返回未登录，查会话既不能证明登录成败，也不能恢复服务。

同一套「结果未确认 + 查询核对」已经铺到多个写操作页面，但本次的主目标是先把登录做成「成功进系统，失败直接说清原因、按钮随时可再试」。全站通用的错误到文案映射是登录能够成立的配套规则，也一并写入，供其他页面在 P1 对齐。

现网只读核对（2026-11-13，以 `E:\tts-erp` 源码为准）见第 11 节。

chen 已于 2026-11-13 确认第 4 节描述的理想登录交互。

## 2. 目标

1. 登录只做一件事：成功就进工作台；失败就在当前页用一句人话说明原因，按钮立刻可再试。
2. 去掉登录页「查询当前会话 / 允许手动重新登录」整套门闩；登录的成功或失败都按确定结果处理，不再出现「结果未确认」。
3. 全站同一类失败用同一套文案和动作（能否重试、要不要倒计时），作为登录改造的配套，并在 P1 推广到其他页面。
4. 非登录页的非幂等写操作在超时或断网时，同样直接报错、按钮可重试、不加核对流程，也**不加**「操作可能已生效」提示（第 6 节，已由 chen 拍板）。登录页本身按第 4.3 节处理。

## 3. 范围

### 3.1 范围内

- **P0：登录页**（`/v2/auth/login`）的完整交互，以及它依赖的全局错误分类与文案映射
- **P1：** 全部 18 个工作台页面（`/v2/pages/*`，清单与 `tts_erp_v2/accounts/pages.py` 的 `PAGES` 一致）：控制台、重点关注 SPU、SPU ROI、利润劣化告警、广告日明细、采购工作台、店铺注册、枚举映射、运行配置、定时任务、用户管理、拦截配置、拦截记录、拦截统计、视频发布、资产管理、数字人、换装视频
- 辅助页：新店接入授权（`oauth-onboard`）、授权/无权限等结果页（`message`）
- 工作台壳层上的会话操作（如退出登录）若走同一套前端 API 客户端，一并纳入文案与动作规则

### 3.2 范围外

- 不改后端业务逻辑、限流阈值、会话策略；若文案映射需要稳定的 `code` 字段，由架构师在技术方案中决定是否补，不在本 PRD 展开实现。
- 不改 `prd/prototypes/`。登录异常态如需补到原型，另开任务，不阻塞本次开发。
- **Chrome 插件不在本次范围**（`plugins/` 下 ads-data-sync、miaoshou-order-capture、monitor、order-data-sync、tts-request-intercept 等），错误提示后续另议。
- `tts_erp_v2/api/v2/auth.py` 中遗留的 `_LOGIN_HTML` 内联登录页：现网登录已切到前端模块（`MIGRATED_PAGE_IDS` 含 `login`）。**架构师确认（2026-11-13）：现网不可达，本次不改**，不在实施范围。

## 4. 理想登录交互（已确认）

### 4.1 主流程

1. 打开登录页，输入用户名和密码，点「登录」。
2. 请求发出时，按钮变成「登录中…」并暂时不可点，防止连点。
3. 成功：进入服务端给出的 `next`（原页或默认控制台）。
4. 失败：立刻在**提交按钮上方**用一句人话说明原因，按钮马上恢复可点（429 冷却期间除外）。用户改完或等一会儿就能再试。
5. 全程没有「查询当前会话」或「允许手动重新登录」。

若打开登录页时已有有效会话：直接进入工作台，不必再登一次。**架构师确认（2026-11-13）：现网不会自动进工作台。** P0 补齐为：会话有效时，`GET /v2/auth/login` **302** 到 `next`（默认控制台）。

### 4.2 原则

登录要么成功进系统，要么失败并说清楚原因，**结果都是确定的**。不要把 503、超时、断网当成「结果不确定」去走核对流程。登录请求本身不会改已有业务数据；没拿到 Cookie 就是没登上，按失败处理即可。

失败后不要清空已填的用户名；密码是否保留按现网习惯，不必额外改。

### 4.3 异常与处理

| 情况 | 用户文案 | 按钮与下一步 |
| --- | --- | --- |
| 请求进行中 | 按钮文案为「登录中…」 | 禁用，防止重复点击；请求结束（成功或失败）后按结果恢复 |
| 用户名或密码错误（401） | 用户名或密码错误 | 按钮立刻可再点；保留已填用户名 |
| 请求太频繁（429） | 登录过于频繁，请 N 秒后再试（N 取自 `Retry-After`） | 倒计时期间按钮禁用，到 0 秒自动恢复可点，到点**不自动重发**，由用户自己点。修改输入不能缩短等待。若没有可用的 `Retry-After`，退回「登录过于频繁，请稍后再试」，按钮保持可用 |
| 服务暂不可用（500 / 502 / 503 / 504） | 登录服务暂不可用，请稍后重试 | 这是确定失败，不会下发登录态；按钮保持可点，可立即再试。不要查询会话，也不要附加「可能已生效」 |
| 网络断开 | 网络已断开，请检查网络后重试 | 按钮可点。登录按确定失败处理，不加「可能已生效」 |
| 等了 30 秒还没结果（前端超时） | 请求超时，请稍后重试 | 确定没拿到 Cookie，按失败处理；按钮可点。不要说「结果未确认」，也不加「可能已生效」 |
| 字段没填完整（400 / 422） | 缺项或格式问题标在对应输入框下面；如需横幅，用「请检查标红的字段」 | 改正后可再提交 |
| 账号被停用或没有权限登录 | 用户名或密码错误 | **架构师确认（2026-11-13）：现网没有独立 403**，与密码错误一样返回 401「用户名或密码错误」（防止通过文案枚举账号是否存在或是否停用）。本次不改这一策略，登录页按 401 处理，不出现「当前账号无法登录」 |
| 已有有效会话再打开登录页 | — | 会话有效时 `GET /v2/auth/login` 302 到 `next`（默认控制台），不必再提交登录 |
| 从工作台因会话过期被送到登录 | — | 登录成功后回到原页（含原查询串），保持现网 `next` 行为 |

冷却只约束登录提交，不引入查询会话。倒计时以响应头 `Retry-After` 为准（现网客户端已能解析秒数或 HTTP 日期）。

### 4.4 登录页必须去掉的内容

包括「查询当前会话」「使用已查询的当前会话继续」「我已了解，允许手动重新登录」，以及「提交结果未确认 / 请先查询当前会话」这类文案。失败后**不再**把按钮锁到必须先查询才能再点。

## 5. 全站通用错误映射

登录页专用文案以第 4 节为准。下列映射用于工作台其他页面，也是登录分类规则的来源：不再把 500 / 502 / 503 / 504 / 超时 / 断网标成「结果未确认」。

### 5.1 原则

- 文案要短、说人话，并告诉用户下一步；不要把 `HTTP 503` 这类状态码当作主文案（开发排障信息可留在控制台或 `x-request-id`，不展示给用户）。
- **直接报错，可重试的保持可点**；不要因失败锁死按钮，也不要插入「先查询再允许重试」的流程。
- 429 且响应带 `Retry-After` 时，展示剩余秒数倒计时：倒计时期间禁用对应提交/重试按钮，结束自动恢复可点，**不自动重新提交**。
- 后端 `detail` / `code` 何时优先于默认文案，见 5.3；技术性内容不得原文展示。

### 5.2 映射表

| 场景 | 用户文案 | 可执行动作 | 倒计时 |
| --- | --- | --- | --- |
| 400 请求不合法 | 请求未通过检查，请核对后重试 | 可改完再提交 | 否 |
| 401 登录页（账号或密码错误） | 按第 4.3 节 | 按钮保持可用，可立即再试 | 否 |
| 401 会话过期（已登录的工作台页、壳层请求） | 不在原页展开报错或核对 | 立即跳转登录页；登录成功后回到原页（含原查询串）。登录页、`message`、`oauth-onboard` 不套用此跳转，以免打断当前页 | 否 |
| 403 接口或页内操作无权限 | 没有权限执行此操作 | 不提供无意义重试；不跳转到整页无权限结果页 | 否 |
| 403 页面级（打开无权限的 `/v2/pages/*`） | 独立结果页。标题用「没有访问该页面的权限」，正文说明当前账号没有该页权限、如需开通请联系管理员；主按钮「返回控制台」，进入 `/v2/pages/dashboard` | 不重试原页 | 否 |
| 404 | 要找的内容不存在，请刷新后再试 | 可刷新后重试 | 否 |
| 409 冲突 | 数据已变化，请刷新后确认再提交 | 可刷新后重试 | 否 |
| 422 校验失败 | 横幅用「请检查标红的字段」；**字段级错误显示在对应字段下方** | 改正后可再提交 | 否 |
| 429 过于频繁 | 操作太频繁，请在 N 秒后重试（N 取自 `Retry-After`） | 倒计时结束后可重试；期间禁用对应按钮 | **是**。若响应没有可用的 `Retry-After`，退回「操作太频繁，请稍后再试」，按钮保持可用 |
| 500 服务器错误 | 服务出错了，请稍后重试 | 可重试 | 否（若意外带了正数 `Retry-After`，按 429 同样展示倒计时） |
| 503 服务不可用 | 服务暂不可用，请稍后重试 | 可重试 | 同上，仅当带了 `Retry-After` |
| 502 / 504 网关失败或上游超时 | 服务暂时无响应，请稍后重试 | 可重试；非登录页的非幂等写也不附加「可能已生效」，见第 6 节 | 否 |
| 网络断开（请求未发出或连接中断，前端未收到 HTTP 状态） | 网络已断开，请检查网络后重试 | 可重试；非登录页的非幂等写也不附加「可能已生效」，见第 6 节 | 否 |
| 30 秒前端超时 | 等待超时，请稍后重试 | 可重试；非登录页的非幂等写也不附加「可能已生效」，见第 6 节 | 否 |

### 5.3 后端可读 detail 何时优先

默认用 5.2 的文案（登录页用第 4.3 节）。仅在同时满足下列条件时，用后端返回的可读说明替换横幅（或补在默认文案之后的一句短说明里）：

1. `detail` 是单行字符串，长度不超过 80 字；
2. 内容面向用户：以中文为主，能独立读懂；
3. **不是**技术内部信息。以下一律不展示：异常类型名或堆栈（如 `auth store unavailable: OperationalError`）、英文内部短语（如 `too many login attempts`、`rate limit exceeded: …`）、权限码或角色名（如 `requires page:users`、`requires readwrite`）、原始 JSON / 校验数组、request id、密钥或堆栈片段。

补充约定：

- 若响应带有稳定的业务 `code`（前端客户端已能解析符合 `^[A-Z][A-Z0-9_]{0,79}$` 的 `code`），且前端为该 `code` 准备了中文映射，则 **`code` 映射优先于 `detail` 原文**。现网如资产管理已对 `ASSET_IN_USE` 等做了映射，应并入同一套共享表，而不是各页私有一份。**架构师确认（2026-11-13）：业务 `code` 作为映射首选；已有中文映射并入共享表；本次不批量给后端补 `code`。**
- 422 字段错误仍走字段下方（可继续使用现有的安全 type 映射，如「请填写此项」「内容过短」）；不要把 `detail` 数组整段渲染成横幅。
- 现网登录 401 的 `detail` 已是「用户名或密码错误」，与本表一致，可以直接用。登录 503 / 429 的 `detail` 属于内部英文，必须走第 4.3 节默认文案。

## 6. 超时与断网时的非幂等写操作（已拍板）

**本节不适用于登录。** 登录在超时、断网、502 / 504 时一律按第 4.3 节确定失败处理，不加「操作可能已生效」。

**已拍板（chen，2026-11-13）：采用方案 A。** 非登录页的写操作（含非幂等写，例如立即执行同步任务、发布视频、修改并发布配置、创建用户、创建店铺或映射、上传素材、触发生成等）在超时、网络断开、502 / 504 时，与读操作、幂等写一样：**只显示第 5.2 节文案，直接报错，可重试，不锁按钮，不加核对流程，也不附加「操作可能已生效，请刷新后确认再重试」。** 500 / 503 同样只显示确定失败文案。

曾考虑过方案 B（报错后再加一句「操作可能已生效，请刷新后确认再重试」），chen 明确不要这句提示，已否决，实施时不得加入。

非幂等写接口清单见架构师技术方案第 5 节（`docs/plans/2026-11-13-login-interaction.md`），不影响本条文案规则：所有写操作都按方案 A。

## 7. 展示形式

| 场景 | 形式 |
| --- | --- |
| 登录失败，以及其它表单提交失败（弹窗表单、页内表单） | 表单内、**提交按钮上方**的内联 Alert（危险态）。现网登录页 Alert 在按钮下方，实施时上移，避免提交后还要往下找 |
| 页面数据加载失败 | 页内 Alert，带「重试」按钮，替代空白或只有转圈后消失 |
| 列表行内操作、弹窗外的轻操作（启用开关、立即执行、删除确认后的结果等） | Toast。现网工作台前端未见统一 Toast 组件，由架构师选型（可复用 HeroUI 或既有 Alert 的轻量浮动形态），但产品要求这类反馈不要撑满主区、也不要打开核对面板 |
| 字段校验（前端即时校验与 422 字段错误） | 显示在对应字段下方 |
| 401 会话过期 | 跳转登录，见第 5.2 节 |
| 403 页面级无权限 | 沿用独立结果页，不在工作台壳层里用 Toast 一带而过。文案与主按钮见第 5.2 节（相对现网标题「无权访问该页面」、主按钮「返回登录页」的差异，见第 11 节） |

错误不得导致白屏。现网入口已有渲染边界和「页面加载失败 / 请刷新」兜底，应保留。

## 8. 优先级

- **P0**：第 4 节登录交互（含登录页去掉核对流程，以及登录所依赖的全局错误分类：不再把 500/502/503/504/超时/断网标成「结果未确认」）。先解开登录 503 的误导流程。
- **P1**：其余 18 个工作台页、`oauth-onboard`、`message`、壳层会话操作的展示统一（第 7 节），以及去掉各页已有的「查询核对」门闩。第 6 节按已拍板的方案 A 一并实施：写操作超时/断网不加「可能已生效」。

## 9. 验收标准

可测试条目如下（登录与其所依赖的全局分类为 P0，其余随 P1；第 6 节已拍板为方案 A，且不用于登录页）。

1. 打开登录页，输入用户名和密码后点「登录」：请求中按钮为「登录中…」且不可再点；成功则进入 `next`；失败则在按钮上方出现人话报错，按钮按第 4.3 节恢复。页面上不出现「查询当前会话」「我已了解，允许手动重新登录」以及查询会话结果区。
2. 登录遇到 503（及 500 / 502 / 504）时：出现「登录服务暂不可用，请稍后重试」；登录按钮在非请求中、非 429 冷却时保持可用；不出现「结果未确认」，也不出现「操作可能已生效」。
3. 登录 401：文案为「用户名或密码错误」，按钮保持可用，不跳转、不锁死；已填用户名仍在。
4. 登录 429 且带 `Retry-After`：展示「登录过于频繁，请 N 秒后再试」及剩余秒数；倒计时期间登录按钮禁用；倒计时结束按钮自动恢复；不会自动重新提交。
5. 登录断网：出现「网络已断开，请检查网络后重试」，按钮可点，无核对流程，无「可能已生效」。
6. 登录等待超过 30 秒：出现「请求超时，请稍后重试」，按钮可点，不说「结果未确认」，不加「可能已生效」。
7. 登录字段缺失或格式错误时，提示出现在对应用户名/密码下方。
8. 停用账号或无登录权限与密码错误一样，返回 401，文案为「用户名或密码错误」；不单独暴露账号是否存在或是否停用，也不出现「当前账号无法登录」。

## 11. 现网证据（只读核对，2026-11-13）

下列为源码现状，供方案对照，不是实施步骤。

- **全局分类**：`frontend/src/shared/api/command-errors.ts` 的 `commandFailure` 仅把 400 / 401 / 403 / 404 / 409 / 422 / 429 视为确定失败；其余状态（含 500 / 502 / 503 / 504）以及非 `ApiError`（断网、超时）一律 `uncertain: true`，文案为「提交结果未确认，请先查询核对；不要重复提交」。确定失败的文案还会带上 `（HTTP {status}）`。后端 `detail` 默认不作为展示文案（店铺 App 凭证等少数英文 detail 有单独字段映射）。`retryAfter` 会从错误对象带出，但本函数不负责倒计时 UI。
- **HTTP 客户端**：`frontend/src/shared/api/client.ts` 已解析 `Retry-After`（纯秒数或 HTTP 日期）到 `ApiError.retryAfter`；403 / 429 或带正数 `Retry-After` 的错误响应会尽早抛出，不因响应体卡住。任意 401 会触发 `setUnauthorizedHandler`。客户端本身**没有**请求超时。
- **30 秒超时**：`frontend/src/shared/api/request-lifetime.ts` 定义 `REQUEST_DEADLINE_MS = 30_000`，超时抛出「请求等待已结束，结果仍需核对」（不是 `ApiError`，会被标成 uncertain）。用户管理页有一份几乎相同的本地拷贝 `frontend/src/pages/users/requestLifetime.ts`。目前仅登录、采购、视频发布、SPU 盈利读写、用户管理、资产管理等模块包裹了该超时；店铺、枚举、运行配置、定时任务、拦截配置等写操作**未见**统一包裹。**架构师确认（2026-11-13）：** P0 登录已有 30 秒超时，只改文案为「请求超时，请稍后重试」；P1 在 `requestJson` 统一包一层，对象存储直传和 ZIP 下载不套。
- **401 跳转**：`frontend/src/main.tsx` 在非全屏页（即非登录 / message / oauth-onboard）把未授权处理登记为跳转 `/v2/auth/login?next=当前路径与查询串`。登录成功后 `leaveLogin(next)` 回到原地址。此行为应保留。
- **登录页**：`frontend/src/pages/login/index.tsx` 在 `uncertain` 时进入 recovery，渲染「查询当前会话」等整块；503 被单独改写为「登录服务暂不可用；提交结果未确认，请先查询当前会话」。401 已改写为「用户名或密码错误」。请求中已显示「登录中…」。`blocked` 在 pending、冷却或 recovery 未放行时为真，所以 503 后按钮会被锁住。429 会按 `retryAfter` 进入冷却并禁用按钮，但界面只说「请等待服务端指定的冷却时间…」，**不展示剩余秒数**。
- **后端登录**：`tts_erp_v2/api/v2/auth.py`  
  - `POST /v2/auth/login` 限流命中返回 **429**，`Retry-After` 与 `retry_after_s`，`detail` 为 `too many login attempts`，不下发 Cookie。限流来自 `tts_erp_v2/middleware/session_auth.py` 的 `login_throttle_hit`（默认每客户端每分钟 10 次，环境变量 `TTS_ERP_LOGIN_RATE_LIMIT`）。  
  - 认证失败返回 **401**，`detail` 为「用户名或密码错误」，不下发 Cookie。  
  - 访问用户库异常返回 **503**，`detail` 为 `auth store unavailable: {异常类型名}`，在 `set_cookie` 之前返回，**确定不下发 Cookie**。  
  - `GET /v2/auth/me` 在库异常时吞掉错误，返回 `{"authenticated": false}`（HTTP 200），所以「查询当前会话」在 503 场景下只会看到未登录，不能解释原登录结果。
