# 前端开发规范：HeroUI 优先与组件复用

> 状态：**用户已确认的开发标准**（2026-10-23）。React 工程地基及 P1 `dashboard` / `intercept-requests` 已验证并合入，阶段证据见[实施计划](../plans/frontend-p01-implementation.md)；其余迁移阶段和生产部署未完成，本规范不构成后续运行时变更授权。
> 适用：ERP 运营前端的新工程、新增页面和逐步迁移的页面；不要求本次批量重写旧页面。
> 不适用：`plugins/` 内独立 Chrome 扩展，其技术栈和发布规则由各插件仓库管理。
> 迁移设计见[前端渐进式迁移技术方案](../plans/frontend-progressive-migration.md)。

## 1. 目标与优先级

本次工程化是为组件复用、TypeScript 类型约束和开发热更新服务，不是以复刻旧外观为目标。

1. 优先使用**免费开源 HeroUI 的原生组件、公开 API、默认样式和官方示例**。
2. 现有布局不是硬约束：当复刻需要深改 HeroUI 或大量样式时，调整布局，不让组件迁就旧皮肤。
3. 保留有效的业务信息、操作能力和必要确认；布局变化不能成为删除业务能力的理由。
4. HeroUI 没有覆盖的能力可以独立实现，包括只有付费产品才提供现成实现的通用布局；不购买
   HeroUI Pro 或付费模板，不复制未获授权的付费源码。
5. 公共能力必须复用；页面专用内容允许定制。不可用“全站统一”强行抹平页面的真实业务差异。

技术方向为 **React + TypeScript + Vite + HeroUI + Tailwind CSS**。具体依赖版本和锁文件由
工程落地阶段验证、提交；本规范不声称这些依赖已经安装。初期仍与 FastAPI 同源、同包交付，
独立部署、SSR、Next.js 和整站视觉重设计不属于默认范围。

## 2. 三层组件边界

| 层级 | 典型职责 | 约束 |
| --- | --- | --- |
| 应用骨架 `AppShell` | 导航、侧边栏、Header、内容容器、需要时的 Footer、窄屏导航 | 全站同一实现；集中维护响应式、折叠、焦点与滚动行为 |
| 共享组件 | 已有多个消费者、语义一致的状态反馈、确认交互、筛选结构等 | 先查 HeroUI 是否已覆盖；确有复用需求再组合或抽取，不预建万能组件库 |
| 页面/功能组件 | 盈利证据、采购工作区、发布任务详情等 | 可按业务定制；复用骨架和共享能力，不复制导航、页头、会话或网络基础设施 |

### 2.1 应用骨架的单一实现

- Header 的标题、描述、面包屑和操作区通过**配置或内容插槽**提供；不得分别为每个页面复制
  Header，也不得让共享 Header 导入某个页面的数据模块。
- 侧边栏的页面标识、分组、标签和可访问入口以服务端页面目录及授权结果为准；前端不能维护
  另一份权限矩阵。当前权威目录为 `tts_erp_v2/accounts/pages.py`。
- Footer 若有全局用途，内容和展示策略统一定义；页面自己的分页栏、统计说明不是应用 Footer。
  不为“组件齐全”而新增无实际内容的 Footer。
- 内容区的宽度、留白、滚动容器等公共规则集中定义；页面只选择少量有实际消费者的语义选项，
  不散布相同布局类和断点代码。
- 页面可以向 Header 提供专属操作，但操作的数据和提交逻辑仍归该页面，不挪入骨架。
- 禁止 `if (pageId === '某页')` 一类业务分支蔓延到通用组件；纯路由高亮不属于此禁令。

### 2.2 复用与封装的判断

先复用 HeroUI，其次组合已有项目组件，最后才新增共享组件或独立实现。

- Button、Input 等已经满足需求的 HeroUI 控件直接使用，不机械再包一层同名组件。
- 自建共享组件应有清晰的公共职责和稳定接口；骨架天然跨页复用，无须等页面复制之后再抽取。
- 对业务组件，先核实实际消费者和语义是否相同；“看起来都是一个表格”不等于应共享整个页面。
- 一次性业务视图留在页面目录；重复需求出现后再抽取，不能以想象中的复用制造巨型配置系统。
- 共享组件不能请求特定页面的业务 API、内嵌权限真相或执行盈利计算。
- 不为同一公共能力同时引入两套 UI 库；确有第三方专业能力缺口时，记录能力对照、许可证、
  依赖成本、维护状态和边界后评审，不默认引入另一整套设计系统。

## 3. 样式与缺失能力

### 3.1 允许的低成本适配

- HeroUI 原生 variant、size、状态和组件组合。
- 必要的少量 Tailwind 工具类，用于组件库未提供的布局、间距和响应式组织。
- 集中维护的主题变量、全局样式入口，以及确有必要的业务可视化样式。
- 自建轻量、可复用的页面骨架；这不意味着必须开发自己的 Button、Modal 或表单控件。

目标是**少维护样式**，不是只把 `.css` 文件换成长串重复的 Tailwind 类。公共布局类只在骨架
中维护；不要把旧的暖纸皮肤、Bootstrap 布局和所有像素参数原样搬进新工程。

### 3.2 默认禁止的深度定制

- 修改或 fork HeroUI 源码来迎合旧布局。
- 依赖未公开的内部 DOM、内部选择器或内部状态实现覆盖。
- 大量 `!important`、跨页面全局选择器覆盖、逐页重建同样的布局和断点。
- 为了统一外观重新实现 HeroUI 已有的焦点管理、键盘交互、弹层或基础表单能力。
- 未经能力验证就声称“HeroUI Table 可以无损替换所有专业表格”。

出现缺口时，在现有功能设计/迁移记录中说明：**需要的业务能力 → 原生能力为何不足 → 现有
可复用实现 → 最小补充 → 所有者和消费者 → 验证方式**。页面专用内容无需伪装成通用组件；
通用内容必须集中实现。不能借此新增一份与原组件竞争的状态真相。

## 4. 数据、权限和依赖方向

推荐依赖方向：`页面/功能 → 共享组件、服务客户端`，`应用入口 → AppShell、页面模块`。
共享组件和骨架不得反向依赖页面；网络客户端不得导入 UI 组件。

- React 管展示状态、用户交互和请求生命周期，FastAPI 继续拥有业务规则、精度、查询范围和授权。
- 前端计算严格遵守根目录 `AGENTS.md` 的 **Frontend calculation boundary**；本规范不另立公式。
- 金额字符串、长 ID、`null`、零和负数按现有 API 契约处理，不经 `Number` 粗暴转换后当成权威值。
- 页面、API 与资产路径通过同一个路径工具消费服务端 `root_path`；不在页面写死 `/tts`、端口或域名。
- 浏览器继续使用 HttpOnly 会话 cookie 和现有 CSRF 约定，不把会话或 API key 存入 localStorage。
- 隐藏菜单和禁用按钮只是展示；服务端授权仍是最终判定。未登录、无权限、限流和服务异常不能
  合并成同一种空列表或跳回首页。
- 旧页面仍可使用旧技术栈直到其迁移批次验收；一个文档标准不代表线上已经切换。迁移前须与
  相关模块 owner 协调，不得直接推翻正在实施的其他方案。

## 5. 用户体验与验证

组件替换必须覆盖相关场景，不以能编译或截图好看代替验收：

- 读取：加载、真实数据、空结果、部分数据/缺失字段、失败、重试。
- 编辑：校验失败保留输入、提交中防重复操作、成功反馈、取消以及结果不确定时不自动重放写请求。
- 授权：匿名、正常会话、只读、缺页面权限、会话到期/吊销；403 不冒充未登录。
- 可访问性：控件有可访问名称，键盘可用，弹层焦点进入/返回正确，状态不只靠颜色表达。
- 响应式：真实长名称、密集列、无图、手机宽度和桌面宽度；允许表格容器滚动，不允许全页意外溢出
  或为缩窄页面而静默丢失业务列。
- 视觉验收：标题存在、数据能显示、全页不溢出不等于页面可用。至少人工查看手机、普通桌面和代表性
  超宽屏的当前编译产物，核对导航排列与可点击区域、KPI 数字/说明层级、列表列对齐和状态信息密度；
  用语义布局断言防回归，不以仅检查类名或保存未查看的截图替代。合成/隔离页面与用户实际运行版本的
  验证范围须分别说明，不把候选验收通过说成已确认用户现场可用。
- 复用：修改一次导航/Header 能在所有已迁移页面生效；至少两个不同页面验证同一骨架，不能
  每个页面都有自己的导航和 Header 副本。

HeroUI 内容槽有自身布局默认值，例如 Card.Content 默认纵向排列；页面应通过公开 API 或内层布局容器
表达所需排列，不全局改库样式。按钮式链接按[官方组合方式](https://heroui.com/en/docs/react/getting-started/composition)
复用 `buttonVariants` 与原生链接，避免在同一元素上叠加冲突的 Link/Button 两套组件样式。

测试入口遵守[测试指南](agent-testing.md)，包括新增前端测试的集成。不得以“纯前端”为由绕过
仓库唯一隔离入口；新的前端测试选择器在 runner 接入并验证前不能当成现成命令使用。
浏览器渲染回归优先复用现有 `tests/browser/` 和[布局巡检](browser-ui-layout-audit.md)的能力。

### 5.1 本次交付不做灰度

用户于 2026-10-24 明确：服务流量较少，本次改造和必要验收完成后直接合并 `master` 启用，
**不设计灰度开关、按用户/流量分批放量或流量观察等待流程**。开发任务可分片实现和验证，
但不是生产放量批次；旧资源确认无消费者并验证替代完成后即可清理，不等待回退期。
保留功能、权限、真实读写和隔离数据库安全验证。隔离测试中的数据通路探针不是流量灰度，
不因此新增发布系统或延长交付流程；出现故障仍可通过 Git/同版本完整发布包撤销。

## 6. 开发与评审检查表

- [ ] 该能力是否已有 HeroUI 原生实现或现有项目组件？
- [ ] 导航、Header、Footer、内容骨架是否确实共享，而非复制后只改类名？
- [ ] 页面差异是否通过组合/插槽表达，共享层是否没有业务页面分支？
- [ ] 是否避免机械包装控件、过度抽象和大量样式覆盖？
- [ ] 自建部分是否区分通用与页面专用，并说明原生能力缺口？
- [ ] 业务计算、权限和路径是否仍各有一个权威所有者？
- [ ] 验证是否包含真实内容、交互状态、权限、窄屏和键盘，而不只是构建成功？
- [ ] 对旧脚本、样式、适配层是否有明确退出条件，未删除其他页面仍依赖的公共资源？
