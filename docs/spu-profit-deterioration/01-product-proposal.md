# 《SPU 盈利表现对比与变化提示》产品方案

> 文档版本：PRD 评审稿 v2 · 更新日期：2026-10-07。
> **已确认：7 天主参考、3 天看近期变化，不做阈值告警。**其余方案细则待评审；本文不是实现完成声明或上线批准。
> 本次只修改产品方案，不修改现有页面名称、访问地址或应用实现。
> [技术设计](02-technical-design.md)、[历史回测](02a-backtest-report.md)、[实施计划](03-implementation-plan.md)、[测试计划](04-test-plan-and-results.md)仍包含旧告警方案；后续须对齐，不能用旧阈值、严重程度、历史确认规则替代本版本需求。

## 1. 决策摘要

**唯一目标：帮助运营人员看清 SPU 的盈利表现及其变化，为后续运营策略调整提供清晰、可信的数据依据。**

- **看谁：**从全局经营数据中查看持续运营的 SPU，避免极少量订单或长期无活动样本淹没正常经营对象；也能核查指定 SPU。
- **看什么：**同一 SPU 两期的 ROI、净利润原值及变化，同时看订单数、广告消耗，理解这些变化有多少依据。
- **怎么看：**【已确认事实】7 天用于主要参考，3 天用于观察近期变化。分别与前一个等长、不重叠周期比较，不把 3 天涨跌单独当成持续改善或恶化。
- **不做什么：**【已确认事实】本版本不做阈值告警，不做告警/严重程度筛选、历史确认升级或告警数量统计；不自动给出加投、停投等策略结论。
- **用户得到什么：**能说清“盈利表现怎样、最近发生了什么变化、依据是否足够”，再由运营决定继续观察、查证或调整策略。

首版只围绕“选范围 → 看对比和依据 → 查盈利详情 → 人工判断”组织页面，不再扩展告警系统。ROI 与净利润可能方向相反，3 天与 7 天也可能方向相反；这不自动代表数据出错。

### 2.2 为什么采用 7 天＋3 天

2026-10-07 的只读数据复核覆盖两个越南店铺，截至店铺当地 **2026-10-06**。为保持比较范围一致，先按“库内累计已付款订单至少 3 单、近 7 天有出单”筛出 **23 个 SPU**；这只是本次复核范围，不等于最终默认活动条件已定稿。

| 同一批 SPU 的观察结果 | 最近 3 天 vs 前 3 天 | 最近 7 天 vs 前 7 天 |
| --- | --- | --- |
| 本期只有 0～1 单 | 20/23（87%） | 11/23（48%） |
| 两期都有出单 | 5/23（22%） | 18/23（78%） |
| 两期 ROI 都可计算 | 11/23（48%） | 19/23（83%） |

3 天有订单的 12 个 SPU 中，9 个只有一单；7 天本期有单则由筛选条件保证，不能把“没有零单”当成独立的稳定性证据。**累计至少 3 单，也不保证每个比较周期都有足够订单。**

用当前事实和估值回算过去 14 个截至日，在已有至少 14 天经营信号、两种窗口均可比较且方向非持平的相邻观察日配对中：

| 变化方向翻转 | 3 天 | 7 天 | 配对数量 |
| --- | --- | --- | --- |
| ROI 从升变降或从降变升 | 29.0% | 13.5% | 200 组 SPU×相邻观察日 |
| 净利润从升变降或从降变升 | 28.6% | 12.3% | 318 组 SPU×相邻观察日 |

经营信号以首次出单或正广告消耗为观察起点，不是已验证的上市时间。以上不是历史页面快照，也不是误判率：真实转折会产生翻转，滚动窗口相互重叠，ROI 可计算也不证明采集完整或足以决策。不能推广为所有店铺的长期最优周期。

结论是：**7 天与 3 天是及时性和稳定性的折中，不能当成同等可靠的证据。**3 天用于较早看到变化，7 天用于结合较多数据观察整体方向，二者都须结合实际订单和消耗。

另有 35 个累计至少 3 单、近 7 天无单的 SPU 仍有广告消耗，占该累计订单范围近 7 天消耗的 5.24%。因此“7 天无单”不能直接等同于停止运营；是否纳入默认范围待 Q-01 确认。

复核采用同一计算快照、金额先聚合再计算的统一盈利口径，不平均日 ROI，不输出商品或订单行级标识；汇总证据可按协调任务 `spu-3d7d-recheck` 追溯。数据复核不是用户效果测试，也不证明源数据采集全部完整。

### 2.3 首版范围

**包含：**店铺与 SPU 范围、7/3 天对比、两期盈利原值和展示变化、订单/消耗依据、数据时间与限制、已有盈利详情及失败恢复。

**排除：**1 天或其他对比窗口、“全部窗口”混合列表、阈值告警和管理流程、严重程度/告警状态筛选、历史确认升级、告警统计、通知、商品排名、新趋势图、单 SPU 预测、自动策略推荐/执行、策略保存或审批。已有入口不变，不代表保留旧告警交互；本次文档更新也不表示已从线上删除旧功能。

## 3. 场景与方案选择

### 3.1 核心任务

| 场景（待验证） | 用户任务 | 成功结果 |
| --- | --- | --- |
| 日常查看全局经营表现 | 选择店铺及持续运营范围，先看 7 天，再按需看 3 天 | 说清 ROI、净利润的方向及订单/消耗依据，知道哪些变化还需观察 |
| 指定 SPU 查证 | 查看这个 SPU 的两期指标，必要时进入盈利详情 | 分清两项指标及两个时间尺度，不因一单或零分母误读涨跌 |

不采用“只列告警名单”或“自动判断该怎么投放”。3 天与 7 天相反可能是近期转折，不自动判其中一个错误，也不自动合成为“整体变好/变差”。

P0＝完整、可信地完成核心任务所必需；P1＝降低理解或核查成本。所有需求属于首版评审稿；未决细则和现有能力差异仍须在开发前对齐。

| R-002 | ROI 与净利润各变了多少 | 两期原值、差额及展示百分比 | P0，直接支撑目标 | 统一盈利口径、R-001 |
| R-003 | 变化是否容易被少量订单影响 | 两期订单/广告消耗及时间尺度说明 | P0，防止短期波动被过度解释 | R-002、实际数据依据 |

## 4. 用户路径与产品结构

1. **进入现有页面。**沿用当前访问权限；未登录或无权限先处理访问，不显示受限业务数据。
2. **选范围。**选店铺，默认查看持续运营范围，也可查指定 SPU；默认 7 天，可切换 3 天。回显实际截至日和两段日期。
3. **读对比与依据。**先读两期 ROI、净利润，再结合订单数、广告消耗。少量订单和缺失不自动判成异常或稳定。
4. **看近期变化。**按需切换 3 天；窗口改变只改变比较周期，不因 3 天无单或 ROI 为空而悄悄换一批 SPU。
5. **查证详情并判断。**进入选中 SPU 的盈利详情，或继续观察；运营判断和策略执行留在既有业务流程。

页面仅需条件/日期、对比列表、范围统计和详情入口。主要阅读层放两期盈利指标，订单/消耗与限制紧邻展示；具体视觉稿待设计评审，不新增告警区域或规则配置页。

## 5. 功能规格

### 5.1 R-001：选择并确认范围

| 输入 | 规则与默认 |
| --- | --- |
| 店铺 | 必选，只能查询有权限的店铺；无可用店铺时说明原因，不自动换店 |
| SPU | 默认持续运营范围；可用现有精确查询，最多 100 个正整数内部编号；非法输入保留并提示，不退回整店 |
| 活动范围 | 【方案建议】默认排除累计订单不足 3 单等极小样本；累计指截至日之前库内可用历史，不承诺真实运营全历史完整。近期活动条件依 Q-01 定稿；显示已应用条件，精确调查允许绕过活动排除但不隐藏数据限制 |
| 窗口 | 默认 7 天，辅助选项 3 天；不提供 1 天或全部窗口。切换时保持店铺、SPU 范围和截至日 |
| 截至日 | 店铺当地日期；默认目标为当地前一日。若结果滞后须显示实际截至日，不把最后可读结果冒充最新完整结果 |

设截至日为 `A`，两端包含：

| 窗口 | 本期 | 上期 |
| --- | --- | --- |
| 7 天 | A−6 至 A | A−13 至 A−7 |
| 3 天 | A−2 至 A | A−5 至 A−3 |

例：A＝2026-10-06，7 天对比 9 月 30 日—10 月 6 日与 9 月 23—29 日；3 天对比 10 月 4—6 日与 10 月 1—3 日。两期不重叠，不用 UTC 日替代店铺当地日。

| 验收 | 可观察结果 |
| --- | --- |
| AC-001（R-001） | 首次进入默认 7 天；切换 3 天后准确回显两段日期，不混入 1 天或全部窗口 |
| AC-002（R-001） | 精确查询活动条件之外、但有可用数据的 SPU 时仍可查证；说明活动条件不生效及数据限制 |
| AC-003（R-001） | 非法或超限 SPU、非法日期/窗口有修正提示并保留输入，不返回另一范围冒充结果 |
| AC-004（R-001） | 改条件回第一页、关闭旧明细；合法查询条件可从链接恢复，不携带凭证；切换窗口不悄悄删掉少样本 SPU |

### 5.2 R-002：看清两项指标变化

每个 SPU 在选中窗口只展示一条结果，分别呈现本期/上期 ROI、净利润、差额和方向。单位清楚：净利润、消耗按现有 CNY 口径，ROI 为比率；不混用广告平台的广告归因 ROI。

- ROI 由周期累计金额按统一口径计算，不能平均日 ROI；净利润按周期聚合。
- 差额为本期减上期。仅上期大于 0 且两期有值时展示百分比；上期为 0、负数或缺失时为“—”，保留可计算的差额。
- 缺失值不补 0；零消耗导致 ROI 无值时说明原因。有消耗却无单、或 ROI 为 0，不自动当作数据错误。
- 含未结算平台费估算时说明；历史数值可能随已确认退款、当前成本或汇率更新，不能称为固定的最终会计利润。
- 箭头、差额、百分比是展示值，不形成告警、资格判定或业务总计，也不改变查询范围。权威盈利计算遵循[开发契约](../business/spu-profitability.md)。

| 验收 | 可观察结果 |
| --- | --- |
| AC-005（R-002） | ROI 从 2 到 2.5、净利润从 100 到 80 CNY 时，分别显示 +0.5/+25% 与 −20 CNY/−20%，不合成一个好坏结论 |
| AC-006（R-002） | 上期为 0 或负数时不硬算百分比；原值与可计算差额仍可读 |
| AC-007（R-002） | 零消耗或指标缺失显示“—”及原因，可用指标仍保留；真实 0 与缺失能区分 |
| AC-008（R-002） | 改变展示舍入不改变 SPU 范围、订单/SPU 统计或产生新的判定标签；能查到日期、单位和估值说明 |

### 5.3 R-003：展示判断依据，不建立告警等级

两期订单数、广告消耗与盈利原值一起读。累计至少 3 单不等于两期样本充足；**不新增每期最少订单、消耗或降幅的告警门槛，不按这些门槛屏蔽结果**。

3 天说明其更易受少量订单、投放节奏及不同星期组合影响；7 天覆盖完整星期，但也不能保证每个 SPU 数据充足。两种窗口相反时保留各自原值、日期和方向，不自动称为误报、恢复或持续恶化。

| 验收 | 可观察结果 |
| --- | --- |
| AC-009（R-003） | 能同时读到两期订单数、广告消耗及其对应盈利指标，不必先查看规则或告警标签 |
| AC-010（R-003） | 3 天本期为 0/1 单、但 SPU 满足已应用活动范围时仍显示记录和原值，不自动标为稳定、严重或不合格 |
| AC-011（R-003） | 查看 3 天时能看到短期波动说明；缺少必要事实则说明限制，不以真实零值冒充缺失或反之 |
| AC-012（R-003） | 3 天与 7 天方向相反时分别如实展示；不存在严重程度筛选、历史确认升级或加投/停投命令 |

### 5.4 R-004：说明统计范围

【方案建议】仅保留分析 SPU 数及选中窗口的本期/上期订单数，不保留告警/严重告警数量。SPU 按完整分析范围去重，订单跨 SPU 全局去重；不得相加行级订单数或把当前页当成全范围。

翻页不改变范围统计；窗口改变则按新的两段日期统计。没有可用统计显示“—”及原因，不伪造全 0。

| 验收 | 可观察结果 |
| --- | --- |
| AC-013（R-004） | 同一订单含两个入选 SPU 时，该期订单只计一次；每个分析 SPU 只计一次，没有告警统计 |
| AC-014（R-004） | 翻页不改变全范围统计；切换 7/3 天后订单统计对应新周期，SPU 统计仍依同一已应用活动范围 |
| AC-015（R-004） | 统计失败不显示假 0 或旧条件数值，说明不可用并允许重试 |

### 5.5 R-005：进入盈利详情

明细集中展示所选 SPU、两段日期、盈利原值、订单/消耗、计算时间和限制，并提供已有盈利详情入口。详情必须关联同一店铺/SPU，说明查看的日期范围；若重新估值时间不同，不保证两处逐分相等。

| 验收 | 可观察结果 |
| --- | --- |
| AC-016（R-005） | 展开并进入详情时始终是选中店铺/SPU，日期明确，能返回原查询；关闭明细不改条件 |
| AC-017（R-005） | 可仅用键盘定位、打开/关闭明细及进入详情，不依赖颜色或鼠标 |
| AC-018（R-005） | 无权限与读取失败分别说明，不显示其他 SPU 或泄露数据；原查询仍能返回 |

### 5.6 R-006：数据时间与失败恢复

显示实际截至日、计算时间及必要估算/来源说明。刷新只是重新读取，不承诺触发同步或重算。新条件加载或失败时，旧列表、统计、明细不能冒充新条件结果。

无匹配记录、真实零值、ROI 无值、事实缺失、服务错误分别说明；服务错误提供请求编号。权限沿用现有只读访问，不新增配置或源数据修改能力。

过期结果的读取策略待 Q-03；【方案建议】若保留最后成功结果，应显著显示旧日期和“数据未更新，仅供参考”，不能静默作为当前结果。旧告警任务是否启用，不是本版本新增的产品开关。

| 验收 | 可观察结果 |
| --- | --- |
| AC-019（R-006） | A 条件的迟到响应不覆盖 B 条件；B 失败时不展示 A 的旧数据作为成功结果 |
| AC-020（R-006） | 无匹配时回显条件并允许调整，不说全店正常或无风险；零单但有消耗的可用记录不是错误空状态 |
| AC-021（R-006） | 服务失败、必要事实缺失或没有可用结果时说明原因，不用成功空列表掩盖；能重试或提供请求编号 |
