# 媒体资产库与数字人 — 技术方案

> 范围包括 2026-11-03 的首版以及后续的操作流程调整。
> 范围：在 tts-erp 内新增一个**全局**媒体资产库（图片 / 视频）与**数字人**（人设档案容器）。
> 上游依赖：MinIO 对象存储（已部署，`docker` 容器 `minio`，127.0.0.1:9000）。

## 1. 目标与边界

### 1.1 已确认需求（2026-11-03 用户拍板）

1. **数字人 = 人设档案容器**：名称 + 说明 + 状态 + 一组引用资产。不含 AI 生成能力。
2. **资产与数字人是多对多**：资产可以无归属（全局公共池），也可以同时挂到多个数字人。
3. **全局池**：资产不按店铺切分。
4. **上传通道**：浏览器预签名直传 MinIO（复用既有 `tts_erp_v2/storage/minio_client.py`）。
5. **预览**：图片直出、视频用浏览器 `<video>` 播放预签名 GET URL；服务端不生成缩略图（本机无 ffmpeg）。
6. **白名单与上限**：图片 jpeg/png/webp/gif ≤ 20 MiB；视频 mp4/webm/quicktime ≤ 200 MiB。
7. **存储桶**：新建独立 bucket `tts-erp-media`（`MEDIA_MINIO_BUCKET` 可覆盖）。
8. **页面形态**：两个独立页面「资产管理」「数字人」，权限点 `page:media-assets` / `page:digital-humans`，授权 admin + operator。

### 1.2 v1 非目标

- AI 生成（RunningHub / 换装视频）与本库的对接。
- 与 TikTok 视频发布流水线的联动（`publishing.video_publish_tasks` 仍独立可用）。
- 服务端缩略图 / 转码（无 ffmpeg）。
- 资产去重、版本管理、CDN、配额。

## 2. 架构

```text
浏览器
  │
  ├─ POST /v2/media/assets/upload-url ──> ttsERP ──> MinIO 预签名 PUT
  ├─ PUT  文件 ──────────────────────────────────────> MinIO (tts-erp-media)
  ├─ POST /v2/media/assets/{id}/confirm ──> ttsERP ──> HEAD 校验 size ──> ready
  │
  ├─ GET  /v2/media/assets[?kind=&status=&keyword=&tag=&digitalHumanId=&excludeDigitalHumanId=]
  ├─ GET/PATCH/DELETE /v2/media/assets/{id}
  │
  └─ /v2/media/digital-humans[/{id}[/assets[/{assetId}]]]
```

对象字节流**从不经过 API 服务器**：浏览器直传 MinIO，服务端只保存元数据。

## 3. 数据模型（`media` schema，migration 0073）

| 表 | 含义 |
| --- | --- |
| `media.media_assets` | 一个上传的图片或视频。`kind`、`filename`、`content_type`、`size_bytes`、`bucket`、`object_key`、`status`、`tags[]`、软删 `deleted_at` |
| `media.digital_humans` | 一个人设档案。`name`、`description`、`status`（active/archived）、`deleted_at` |
| `media.digital_human_assets` | 数字人 ↔ 资产多对多链接。`UNIQUE(digital_human_id, asset_id)` |

约束与约定：

- `media_asset_status_check`：状态只有 `awaiting_upload` / `ready` / `failed`。
- `media_asset_size_check`：`size_bytes > 0`。
- 三张表都挂 `public.fn_touch_updated_at()` BEFORE UPDATE 触发器（仓库既有约定）。
- 资产仅在没有未删除数字人引用（含归档）时可删除；资产排他行锁下检查引用，仍被引用则返回 `409 ASSET_IN_USE`，不软删也不删除存储对象。允许删除时采用**软删**（`deleted_at`）+ 对象存储 best-effort 删除。历史已删除资产仍从数字人的资产列表和计数中排除。
- 删除数字人只软删数字人并解绑链接，**资产本身保留在全局池**。

## 4. 对象键布局

```text
assets/<YYYY-MM-DD>/<asset_id>-<slug>.<ext>
```

- 无店铺段：库是全局的。
- 扩展名由**内容类型**决定（`CONTENT_TYPE_EXTENSIONS`），不由用户文件名决定——改名文件无法冒充别的类型。
- 桶由 `MEDIA_MINIO_BUCKET`（默认 `tts-erp-media`）选择，与 `tts-erp-spu-images`、`tiktok-video` 生命周期隔离。

## 5. 上传与确认

1. `POST /v2/media/assets/upload-url`：
   - 服务端先校验 `content_type` 在白名单内、`size_bytes` 不超过该类型的上限；不合规 → 400。
   - 分配 `awaiting_upload` 记录和对象键，签发 PUT URL 后一并提交。
2. 浏览器携带票据的 `required_headers`，PUT 文件到 MinIO。
3. `POST /v2/media/assets/{id}/confirm`：
   - HEAD 对象。对象不存在 → 标记 `failed`，返回 409 `UPLOAD_NOT_FOUND`。
   - `size` 与申报值不符 → 标记 `failed`，返回 409 `SIZE_MISMATCH`（防篡改上传）。
   - 一致 → 置 `ready`，可同时返回预签名 GET URL。已就绪的票据可以再次确认，沿用原入库时间。

MinIO 未配置时，资产和数字人详情仍可读取元数据，预览 URL 返回空值。未就绪的资产同样没有预览 URL。申请票据和首次确认需要对象存储，未配置时返回 HTTP 503。已就绪票据可再次确认，预览链接为空。

## 6. 访问控制

| 端点 | 最低角色 |
| --- | --- |
| `GET /v2/media/**` | readonly |
| `POST / PATCH / DELETE /v2/media/**` | readwrite |

- 路由角色矩阵在 `tts_erp_v2/access/_policy.py`（`/v2/media/` 前缀：GET/HEAD/OPTIONS → readonly，其余 → readwrite）。
- 页面权限点 `page:media-assets` / `page:digital-humans` 由 `accounts/pages.py` 注册，alembic 0073 为 admin + operator 种子授权。
- Cookie 会话的所有写操作要求 `X-Requested-With: tts-erp`（CSRF 守卫）。
- 资产与档案按 ID 单条删除属于 `readwrite` 业务操作，适用于生产库。页面要求确认，接口对会话写入校验 CSRF。素材仍被引用时返回 `409 ASSET_IN_USE`。

## 7. 前端

两页复用应用骨架、HeroUI 和同一个上传协议。自 `0076_media_packs` 起，数字人的主入口是素材包，早期卡片交互记录见下文。

- 资产管理提供「素材包」「视频」「全部素材」。可勾选库内视频新建包或加入已有包，也可从包内选择或上传多段视频。
- 数字人档案显示已关联的公共包。可选现有包，或上传和选择视频建包，随后在同一事务内关联当前档案。已有直接关联单独显示在「管理原有素材」。
- 素材包由名称与视频 ID 组成。同一个包可供多个档案使用。移出视频保留原素材，解除档案关联保留包，归档保留关联。
- 确认入库成功的视频立即属于公共库。部分失败时重试跳过已入库文件，确认失败时重试同一票据。建包请求使用同一创建令牌重试。
- 资产详情列出所属的包和去重后的数字人引用。任何素材包引用或未删除档案的直接引用都会阻止全局删除。
- RunningHub 新建人物模板时读取直接关联与包内就绪视频，按资产 ID 去重。已生成的模板继续使用自己的素材快照。

### 早期卡片交互

- **资产管理**正文直接提供搜索、类型筛选和上传。卡片名称与图片或视频类型同排，类型和标签分别着色。查看、编辑和删除通过卡片打开弹窗，卡片省略引用计数。删除时重新查询关联并由后端事务校验。归档档案的关联也会阻止删除。
- **数字人**档案卡片支持弹窗新建、编辑、添加素材、归档和删除。新建成功后留在档案列表。从归档筛选创建时切回启用中。创建可选一张形象照，点击档案头像可更换。浏览器通过预签名 PUT 直传，确认入库后才把照片关联到档案。取消换图保留当前照片。
- **关联素材**在独立管理视图以卡片显示，支持查看、移除单项、全选和批量移除。返回和面包屑可回到保留状态筛选的档案列表。批量移除只解除目标档案的关联，在同一个事务中完成。
- **添加素材**从档案卡片或关联素材视图打开。默认隐藏已关联项，由服务端过滤。继续加载、搜索和上传保留待添加选择。确认时若部分失败，只剩余未确认的项可重试。
- **标签及上传**复用既有候选、显式开始、对象确认和关联重试流程。形象照只允许图片，沿用图片白名单和 20 MiB 上限。

### 7.1 卡片接口与迁移

- 素材库、关联素材、选材弹窗使用 `GET /v2/media/assets?cursor=&limit=12`。数字人卡片使用 `GET /v2/media/digital-humans?cursor=&limit=12`。在首批传空游标，后续传上一批的 `nextCursor`，值为 `null` 时结束。继续请求需使用相同过滤条件。两类列表按 `updated_at DESC, id DESC` 排序。修改、上传或筛选后从头刷新；继续加载保留已有卡片。
- 旧客户端不传 `cursor` 时仍可使用 `limit` / `offset` 和旧有创建顺序，数字人列表继续返回数组。卡片游标模式返回含 `items`、`total`、`nextCursor` 的对象。
- `POST /v2/media/assets/upload-url` 可用 `isPortrait: true` 分配形象照上传票据。确认后在数字人 POST / PATCH 传 `portraitAssetId`，数字人读取返回 `portraitUrl`。形象照从全局素材查询和关联候选排除。旧照片保留为独立对象。
- `GET /v2/media/digital-humans/{id}?includeAssets=false` 返回档案与关联 ID，管理视图用素材游标按需读取详情。`POST /v2/media/digital-humans/{id}/assets/batch-remove` 接收 `assetIds` 数组，重复移除返回成功并保留素材。
- 迁移 `0075_media_card_feeds` 新增形象照标记、档案外键及游标索引。已有资产默认属于全局库，已有档案的形象照为空。

### 7.5 2026-11-07 原型一致性修订

用户确认的 `media-interaction-map.html` 继续作为业务内容区的页面结构、文案、信息密度和操作顺序依据。正式产品保留唯一应用骨架及真实媒体预览、文件选择和异步恢复；原型的演练导航、占位媒体及故障按钮不进入产品。引用中素材禁止删除的后续指令优先于原型旧文案。

- 素材库：地面页头「全局素材库」，右侧「上传素材」；搜索名称/说明/标签和素材类型后统一搜索。每页四项紧凑预览卡片，显示名称、类型、引用数量和标签；底部左侧始终显示总数/页码，右侧前后页。
- 素材详情：名称为主标题，独立「素材资料」和「哪些数字人在用」两块。详情中的编辑进入「编辑素材资料」，表单底部保存/取消。从数字人打开时提供「返回档案」。引用者顺序与档案列表一致（创建倒序），含归档档案。
- 数字人列表：直接切换「启用中 / 已归档」，单个白色区域内展示紧凑档案行、状态、素材数和操作。详情以名称/说明开头，状态与编辑/归档/恢复/删除在同一操作行；「引用素材 · N 项」右侧只有「添加素材」，下面是素材行和查看/移除操作。引用按添加顺序追加；幂等重复添加不换位，移除再添加排末尾。
- 选择素材：页头常显目标，右侧可上传新素材。搜索下方左侧「隐藏已选内容」默认开启，并显示同条件查询的已隐藏引用数量；右侧本次新增数量、取消及「确认添加（N）」。当前勾选有直接取消入口，卡片提供紧凑预览、名称勾选和「查看预览」折叠大图/视频，不让新增勾选立即消失。
- 上传弹窗复用 HeroUI Modal。素材名称在上，文件入口及原始文件名在下，标签可选。自动名称跟随当前文件，手工填写的非空名称在换文件后保留。空文件或不支持的格式需要重新选择。预览保持比例，视频通过浏览器原生控件播放。标签选择使用 Disclosure、Checkbox 和可移除 TagGroup，展开后搜索全部已保存标签，可新建同名项不存在的标签。
- 两个入口取消或完成都留在原页。资产库成功提示提供详情入口；数字人上传成功时自动关联当前档案并保留原有勾选。传输和确认分别反馈进度，确认与关联失败可独立重试。
- 操作确认：移除引用、归档、删除进入独立「操作确认」内容区，显示具体对象和影响，底部取消/确认。引用中素材列出引用者并禁用删除；放弃未保存草稿仍使用小型确认弹层。

本轮通过固定数据、同等业务内容宽度的逐屏截图比较验证呈现；另保留长名称、375px 窄屏和真实上传阶段的行为验收。页面结构、数据/状态正确与真实运行版本分别记录，测试通过不能替代截图复核。验证记录见实现计划末尾；最终交付须同时更新本地前端包，不能仅合并源码。

## 8. 运维

- **本机前端包**：服务代码新增 React 页面后需重新构建并发布本机前端包（`bash scripts/build_frontend.sh`）。如果两页同时显示「页面加载失败」，先确认当前 `release.json` 对应的 Vite manifest 同时包含 `media-assets` 和 `digital-humans`。

- **新建 bucket**（一次性，加法操作）：

  ```bash
  docker exec minio mc mb --ignore-existing local/tts-erp-media
  ```

- **nginx 上传上限**：`~/setup/nginx/conf.d/services.conf` 的 `location /minio/` 段 `client_max_body_size` 从 `10m` 提到 `500m`（否则 200 MiB 视频会被 413 拒），然后 `nginx -t` + reload。
- **生产迁移与重启由人工执行**：本仓库不自动 `alembic upgrade`，不自动重启服务。
