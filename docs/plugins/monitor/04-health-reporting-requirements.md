# Monitor 最小探活需求与上报字段

> 状态：核心产品规则已逐项确认；本次收敛稿待用户整体审阅。不是实施授权。
>
> 原则：**如无必要，勿增实体。字段从最小集开始，有实际缺口再增加。** 本稿替换此前未经批准的丰富字段草案。

## 1. 已确认的范围

- 同时发现「插件失联」和「插件在线但业务没有推进」，全天运行，不因夜间或周末自动静默。
- 「节点」指插件内部的扫描、规则判断、关停处理环节，不指电脑或安装实例。
- 每店仅一个 monitor 实例；以**真实店铺 ID** 唯一标识，人工店名仅作展示。
- 完全失联后 **3 分钟内发出第一条飞书告警**；内部节点统一按 **连续 3 分钟无实际进展**判异常。
- 同一故障首次通知一次，持续期间不重复；确认恢复后通知一次。
- 全部健康告警统一发一个飞书群，通过 Webhook 发送，读取 tts-erp 现有固定配置；插件不增加健康告警机器人配置。
- **主动停止监控：停止业务节点告警，但独立心跳继续，失联告警仍有效。** 关闭浏览器不能可靠报告原因，按心跳缺失处理。
- 只增加探活，不改变广告规则、真实关停行为、白名单、SKU 保护或原有业务报表。

## 2. 客户端上报：仅四个业务字段

每次只上报一个处理环节的状态；不是上传全量日志或每个环节的复杂运行档案。

| 字段 | 类型 | 必填与来源 | 用途与约束 |
| --- | --- | --- | --- |
| `shopId` | string | 必填；插件已识别的真实店铺 ID | 唯一归属；不能用名称、广告账户 ID、安装 ID 或猜测值代替。与现有 sellerId/ERP 店铺标识的准确映射须在接线时核实，不预先假定等价 |
| `shopName` | string | 必填；人工配置的店名，优先复用现有「通知显示店名」 | 用于飞书展示；重名不合并店铺，改名不改变 shopId。允许空字符串时以 shopId 展示，不额外补自动名称体系 |
| `step` | enum | 必填；产生埋点的处理环节 | 心跳、扫描、规则判断、关停处理；建议 wire 值见下一节 |
| `status` | enum | 必填；该环节的明确状态 | 表达开始、实际进展、完成、失败，以及心跳携带的运行/主动停止意图；建议值见下一节 |

接收与进展时间由**服务端记录**，客户端不传时间戳。鉴权继续使用现有 HTTP header 机制，不增加业务 JSON 字段；服务端必须校验店铺访问范围，知道 shopId 不等于有权写入。

**不增加**安装 ID、worker ID、执行 ID、上下文 ID、版本号、序号、计数、队列明细或错误堆栈；也不预建全历史埋点、通用事件平台、可配置提醒计划或维护审批系统。

## 3. 如何用四个字段表达必要状态

以下是最小协议的建议枚举，待随本稿整体审阅；`progress` 只是同一字段的取值，不是新增字段或节点。

| `step` 建议值 | `status` 建议值 | 采集时机与准确含义 |
| --- | --- | --- |
| `heartbeat` | `running` / `stopped` | 独立定时心跳；分别表示业务监控开启、用户主动停止。两者均证明插件还能上报；stopped 只抑制业务节点告警 |
| `scan` | `started` / `progress` / `completed` / `failed` | 开始列表扫描；完成真实分页等工作；取得并提交完整有效列表；或扫描失败。只收到 Alarm、旧缓存、页面部分列表不算完成 |
| `evaluate` | `started` / `completed` / `failed` | 开始、完成或未能完成本轮规则检查。没有命中广告也可正常完成；原有开关使本轮不适用时，结束该正常分支，不伪称执行了实际关停 |
| `close` | `started` / `progress` / `completed` / `failed` | 监控整个关停处理流程。逐个真实处理结果可形成进展；无需关停也是正常结束。请求/确认失败如实报 failed，不能把流程退出或 API 成功当作广告关闭成功 |

关键语义：

1. **开始不等于进展。** 重复 started、定时心跳、无实质工作的循环不得重置业务进展时间。progress 只能在真实工作单元结束时产生，失败重试本身不冒充有效进展。
2. **业务节点不能互相续命。** 心跳、手动刷新或业务报表成功不能掩盖定时扫描停止；上游失败时不能把后续未执行步骤报成完成。
3. **检查当前应推进的环节，不给尚未轮到的环节制造超时。** 例如正在逐个关停且仍有真实进展，不因整批超过 3 分钟就报扫描/规则卡死；正常等待下一轮扫描时仍须能发现整个循环不再启动。
4. 主动停止时立即尝试上报 heartbeat/stopped，后续独立心跳持续携带 stopped；重新开启时上报 running 并重新建立业务节点的观察起点。不新增单独「维护暂停」功能。
5. 只有服务端收到停止状态才知道停止意图；网络中断时不保证停止通知送达。自动故障、解绑、登录失效不能被误报为「用户主动停止」而静默。
6. MV3 worker 正常挂起/唤醒不视为插件死亡，仍用 Chrome Alarms；心跳不能等待扫描/关停队列释放。

## 4. 服务端判定与通知

- 按 shopId 关联店铺，按 shopId + step 分别观察；仅保存当前判定所需状态、进展时间及是否已成功通知，不为探活预建安装实例/故障事件等额外实体。
- 心跳只更新在线证据及运行/停止意图，不刷新业务节点的有效进展时间。业务停止时不检查扫描/规则/关停的无进展，但继续检查心跳失联。
- 完全失联首报的 **180 秒是端到端目标**，需给服务端扫描和 Webhook 请求预留预算；不能等满 180 秒才开始检查。内部节点以 180 秒无实际进展判异常，调度时延须在实现和验收中明确，不与正常批量总耗时混淆。
- 同一故障已成功通知后不重复发送。发送失败不算「已通知」，允许有界重试；这不是周期重复提醒。恢复消息仅在对应故障确实恢复后发送，不能凭一次普通心跳宣称业务也恢复；用户主动停止业务不冒充故障恢复。
- 失联时告警应表达「失联」，不推断一定是浏览器关闭、电脑休眠或插件崩溃。
- Webhook URL 属于秘密，只供服务端发送使用，复用 [运行配置与凭证管理](../../ops/runtime-config-management.md)，不下发插件、不放进普通 snapshot 明文。已有配置能力不代表已有飞书发送器或 secret 解密 resolver；实施时沿 token_service 边界做最小接线。

## 5. 实施约束与明确不做的事

- ERP 不可达或健康上报失败不能阻塞原有广告监控、关停或插件飞书报表；请求必须有界。
- 不堆积重放历史心跳来制造当前在线；恢复连接后报告当前状态，发送中保持必要串行顺序，避免旧停止状态覆盖新运行意图。若四字段方案存在无法满足验收的缺口，先说明证据再讨论增加字段，不提前扩展。
- 首次有效上报前服务端尚无该插件的存活基线；本稿不声称能发现「从未接入」的插件，也不增加设备登记平台。重启后须保留已有判定与通知状态，不能重复报警。
- 扫描间隔若配置得超过 3 分钟，就与本次无进展规则冲突；实施时必须核对现有配置并显式提示，不暗中放宽已确认阈值，也不另增一组客户端阈值字段。
- 不上传 Cookie、API key、Webhook、签名密钥、App Secret、广告明细、完整请求/响应、配置备份或自由日志。HTTP 2xx 仅在约定持久化完成后返回，遵循 [成功语义](../../api/dumps-data-contract.md)。
- ERP/API、定时扫描 worker 或飞书整体故障时，本机制自身也可能无法通知；这是服务端运维监控的故障域，不能承诺仅靠这条链路发现全部自身故障。
- 本次不增加 ERP 状态页、不接入广告观测入库、不迁移原有业务报表通知；相关需求如有需要再单独讨论。

## 6. 验收清单与下一步

1. 真实 shopId 唯一归属；同名不同店不混淆，人工改名不改变同店状态；请求只含四个业务字段。
2. 在服务端及飞书可用的验收环境中，停止浏览器/切断电脑网络后，180 秒内发出首条失联告警；持续期间不刷屏，恢复后仅一条恢复通知。
3. 独立心跳正常时，分别制造扫描、规则判断、关停无实际进展，持续 180 秒应判异常；重复 started 不续命，其他环节正常不掩盖。
4. 无需关停可正常完成；连续处理多个关停任务且持续有真实进展时，不按整批总耗时误报；失败不伪造关闭成功。
5. 主动停止后，业务节点不再因未推进告警，独立心跳持续；随后关闭浏览器仍失联告警。重新开启后恢复业务观察，不继承停止期间的超时。
6. 上报/通知失败、正常 worker 重建和服务端重启均不破坏原有业务或通知去重；不存在秘密泄露、历史重放续命或停止/恢复意图被明显乱序覆盖。
